Hunting Supply-Chain Malware Across Developer Marketplaces

Why Developer Tooling Needs a Different Playbook

If you drop a suspicious Windows executable (.exe) into a traditional malware sandbox, the signs of trouble are usually clear: it has no valid digital signature, it unpacks hidden code in memory, or it injects into a system process.

Developer extensions for editors like VS Code, Cursor, and Windsurf break all of those assumptions. An extension is essentially a bundle of JavaScript running inside your editor's Node.js process with your full user permissions.

Why extensions blend in

  • No code signing: Marketplace extensions don't carry traditional Authenticode signatures.
  • Noisy by design: Legitimate extensions constantly read workspace files, spawn git or shell commands, and talk to remote APIs.

How attackers exploit the ecosystem

  • The "Sleeper" flip: Publish a harmless 1.4 KB stub today, wait weeks, and push a backdoor as a routine version update.
  • Registry blind spots: Upload a clean build to one marketplace and slip a backdoored build with the same version number onto another.

To catch supply-chain attacks in VoodooBox, I couldn't just rely on manual file submissions, and I couldn't just scrape the "Newest" page of a single marketplace once. I had to build an automated architecture that watches identities across registries and over time.

1. The Supply-Chain Architecture: Wide Intake, Narrow Detonation

Running an extension inside a real Windows VM with a simulated developer session takes several minutes, whereas static code analysis takes seconds of CPU time.

Everything in the supply-chain pipeline is built around one rule: watch everything cheaply, and spend VM time only on builds that earn it.

Every registry feeds one tracker; only questionable builds reach the sandbox

How to read this: Each marketplace has its own collector tuned to how that registry actually behaves. All of them write into a single database table where the same extension on two registries is stored as two separate rows. Only questionable builds move right into the sandbox.

2. Multi-Registry Tracking: "A Version Number is a Claim; a Hash is a Fact"

Tracking Microsoft's official VS Code Marketplace alone is no longer enough. Modern developers increasingly rely on AI-first forks like Cursor and Windsurf, which pull extensions from Open VSX or their own standalone mirrors.

The blind spot became clear when Microsoft published an advisory on a malicious extension masquerading as Claude Code on Cursor's marketplace (Microsoft Security Blog: Inside malicious Claude Code-branded Cursor extension persistent SSH backdoor). Attackers published malicious builds that opened a reverse SSH tunnel and harvested credentials.

That incident is exactly why I built Cursor marketplace support into VoodooBox. At the time my tracker only watched the VS Code Marketplace, where the malicious builds never existed, so it couldn't see them. The backdoored release on Cursor shared its version number with an Open VSX build that showed none of the backdoor's indicators, while a follow-up malicious version existed only on Cursor. Same name, same version, different bytes, and only one registry was serving the bad ones.

Two specialized workflows: Cross-Registry Tamper Checks & Sleeper Watch
How VoodooBox catches byte-level registry tampering (left) and time-delayed placeholder flips (right)
Why I built it this way: Only alerted Cursor builds are saved to disk; identical builds are hashed in stream and discarded, costing bandwidth rather than storage. Meanwhile, the hourly Sleeper Watch ensures a quiet placeholder can never wake up unnoticed.
What about AI Agent Plugins (MCP Servers, Rules & Hooks)?

Cursor plugins aren't packaged as .vsix files. They are live GitHub repositories containing AI prompt rules, shell hooks, and Model Context Protocol (MCP) servers. VoodooBox catalogues plugins daily, compares the commit Cursor reviewed (gitRef) against the repo's live HEAD to spot unreviewed changes, and checks for hidden Unicode characters (invisible prompt injection) or auto-run shell hooks before running suspicious plugins in a dedicated bait harness.

3. Inside the Gate: Static Triage, Unpacking Loops & The Chamber

Before dedicating a VM run to a newly discovered extension, VoodooBox screens it through a fast 7-phase static pipeline. If the code is heavily obfuscated, it routes into an isolated unpacking loop to peel back the layers before deciding whether to escalate into a baited sandbox environment called The Chamber.

How an extension is judged: Static checks, unpacking, and the sandbox gate
Fast triage and unpacking loops peel back obfuscation before spending VM time
How the pipeline protects sandbox time: Static rules flag suspicious patterns. If a script is packed or obfuscated, the isolated unpacking loop decodes it layer by layer without executing it. Only when dangerous intent or high-risk indicators are confirmed does the extension enter The Chamber for full dynamic detonation.

How the Multi-Layer Unpacking Loop Works

Malicious extensions frequently hide their true behavior under multiple layers of obfuscation, such as scrambled text, encoded scripts, or encrypted loaders. Rather than blindly launching every obfuscated script into an expensive Windows VM, VoodooBox peels it open statically first:

  • The Static Layer Unpacker: Runs inside an isolated REMnux container with no network access. It systematically walks through common script packing techniques (JavaScript packers, atob decoding, obfuscator.io string tables, PowerShell arithmetic folding, and batch de-chaining). Each decoded layer is saved and checked with signatures again.
  • The AI Unpack Agent: When a layer is too complex or uses custom cryptography that static rules cannot parse, the local AI Unpack Agent steps in. It operates in a bounded tool loop where it can inspect the layer, run safe JavaScript emulators with recording stubs for Windows Script Host and ActiveX, or run constrained Python decoders. Once it isolates the inner executable or script, the recovered artifact loops back into the pipeline as a new child task.
  • Automated Learning: When the lab encounters recurring obfuscation tricks, an automated engineer cycle drafts a targeted decode plugin for that family. Once benchmarked against the corpus, the plugin joins the static unpacker so future samples peel open in milliseconds without needing agent turns.
  • Headless Ghidra Decompilation: For native binaries (PE files) dropped by an installer or unpacked from an archive, headless Ghidra runs in an isolated container to decompile code and identify risky native API functions before the binary ever touches a live VM.

4. Putting It Together: How the Automated Pipeline Traps Supply-Chain Malware

If you look at the system as a whole, it operates like an automated factory line. The goal is simple: handle thousands of routine updates cleanly, but ensure that any subtle trick, like an empty placeholder waking up or an extension dropping hidden files, immediately triggers deep inspection.

The Complete Pipeline: From Marketplace Intake to Confirmed Verdict
How routine checks hand off to specialized tools only when an extension looks suspicious
The pipeline in four simple handoffs: Static triage rapidly clears harmless code. Obfuscated files are unpacked offline. High-risk candidates enter the baited Windows VM. Finally, anything the malware writes to disk or injects into memory loops back to be analyzed on its own.

Three Design Lessons I Learned the Hard Way

  • Never feed external blocklists into AI prompts: Early on, I passed Microsoft's takedown flag into the sandbox AI prompt as context. When the model saw an extension was on a blocklist, it reasoned backwards and invented a sinister command-and-control story out of routine Microsoft Edge update traffic. Today, external takedown lists are stripped from every prompt and used strictly after the fact to grade accuracy.
  • If a phase fails, drop it, do not score it as zero: When a local AI server is busy or restarting, a missing score of 0.0 must never be averaged in as "0% risk" (which clears malware) or a flat fallback (which causes false alarms). If a phase doesn't run, the remaining weights renormalize automatically.
  • Sandbox capacity is the real bottleneck: Running full Windows VM sessions takes time. Keeping the static gate sharp, and prioritizing active sleeper flips and campaign hits, is what keeps the lab responsive.
